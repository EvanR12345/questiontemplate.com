MEASURED COMPONENT TEST · 28 OCT 2026

Same pixels. Smaller uploads.

A Standard-only test reviewed the same 12 frozen images in four batches. Exact lossless WebP reduced request bytes by 16.8%; the two WebP batches took 15.7% less time in total, including fresh image encoding and verification. This is an observed QC component result, not a measured two-hour video speedup.

What the test measured

48 paid QC calls in PNG / WebP / WebP / PNG order: 24 per encoding, four shared API slots and five outer tasks. Both versions used the same Luna model, low QC reasoning, Standard processing, full prompts, output schema, low image detail, generated image and canonical reference. No images were resized or edited. Original files stayed unchanged.

All 48 returned Standard-tier receipts settled. Actual API cost for the entire comparison was $0.017282717, with no unresolved usage or retries. No GPU was rented for this test. Socket-write timing includes local TLS/kernel acceptance and backpressure; it does not prove when the remote application received every byte. Header waiting still includes transport and provider/server work.

Two batches per encoding are a small sample. Network conditions and model reasoning vary. Batch times include preparation and the adapter, but exclude real project-persistence callbacks, image generation, repairs, narration and rendering. Reference preparation is reported separately for both versions.

Quality and coverage

All 13 unique inputs retained exact decoded RGB and RGBA pixels, modes, dimensions and metadata in the offline comparison. Both encodings produced four blocking reviews out of 24. Major findings had identical per-case frequencies: one of two repeats for cases 00 and 02, and two of two for case 10. No case showed a major defect consistently detected in one encoding and missed in both repeats of the other.

Advisory findings and repair actions still varied, including between repeated requests with the same encoding. This pilot does not establish universal review equivalence. The production candidate is restricted to exact lossless QC transport, with original inputs retained for unsupported images, metadata, decode/encode failure or failed pixel verification. Image generation and final artwork remain unchanged.

Why the GPU schedule has gaps

Accepted chapter plans must exist before their images can start. Starting the GPU after only one plan can leave it waiting for later directing work. The installed Align strategy delays image admission until accepted work covers the forecast planning tail; without matching history it waits for planning to finish. Managed rental starts when generation is actually needed. An externally rented pod still needs its own start and stop controls.

The runtime also limits five tasks across image generation and QC. If all five are waiting for checks, the GPU can run out of work. Smaller QC uploads address part of that wait. A separate durable review queue would be a further change requiring its own recovery, cost and quality tests.

Proposed is not the installed workflow. Its chart omits the five-task generation/QC limit and stops rental after initial image saves, before pending QC and repairs finish. Its 20m49s rental example is therefore not an achieved or runtime-equivalent cost. Installed mode is also a coarse forecast: whole-chapter director blocks and grouped QC can exaggerate contention. The startup comparison now preserves the selected Installed or Proposed mode instead of silently switching it.

What remains unchanged

The 12.3-minute voice estimate, image cadence, model, reasoning settings, check coverage and four-slot API limit remain unchanged. No complete-video timing or cost calibration is revised from this small test. A fresh full production run is still needed to establish the effect on a two-hour video.
